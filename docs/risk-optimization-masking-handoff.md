# 위험 분석 최적화·마스킹 고도화 인수인계

## 다음 세션 시작점

- 브랜치: `feature/#58-risk-optimization`
- 관련 이슈: `#58`
- 구현 커밋:
  - `16f0cc6` 위험 분석 응답과 비동기 수정안 생성 분리
  - `2cf8e60` 민원 관계자 컨텍스트 기반 개인정보 마스킹 강화
- 먼저 `git status --short`와 아래의 DB 적용 정책을 확인한다.

## 해결하려는 문제

기존 백엔드는 FastAPI `/analyze` 약 39초 뒤 `/revision` 약 14초를 순차 호출해 위험 분석
응답까지 약 54초가 걸렸다. FastAPI 직접 호출도 약 39초였으므로 백엔드는 수정안 대기와
장기 DB 잠금을 제거하고, `/analyze` 자체 속도는 AI 서버에서 별도로 개선해야 한다.

## 완료된 변경

- `/analyze` 결과를 저장·응답한 뒤 `/revision`을 별도 작업으로 실행한다.
- 수정안 상태를 `PENDING`, `COMPLETED`, `UNAVAILABLE`, `NOT_REQUESTED`로 관리한다.
- 기본 60분 이상 남은 오래된 `PENDING`은 복구 작업이 `UNAVAILABLE`로 전환한다.
- 수정안 생성 실패 시 성공한 HYBRID 위험 분석을 유지하고 수정안만 `UNAVAILABLE`로 처리한다.
- 외부 AI 호출은 트랜잭션 밖에서 실행하고 저장 시 content hash/version을 재확인한다.
- AI capability·attempt·duration·outcome을 본문 없이 기록하고 분석/수정안 timeout을 분리한다.
- 학생명·교사명·학번·교직원번호를 `PiiMaskingContext`에 담아 다음 경계에 재사용한다.
  - 위험 분석 입력과 Rule/LLM 근거·사유
  - 반복 민원 문맥
  - 수정안, 완충 요약, 교사 답변 초안 출력
  - 관리자 공유용 마스킹 메시지
- 전화번호·이메일·주민등록번호·학급 학생 문맥 정규식은 정적으로 컴파일한다.
- DB 관계자 값은 별도 정규식 없이 긴 문자열부터 literal 치환한다.
- 수정안 상세는 기존 findings 조회로 유지하며 위험 분석 응답에는 상태만 포함한다.

예상 효과:

```text
현재: 위험 분석 응답 약 54초 → 약 39~40초
AI /analyze가 5초로 개선된 이후: 위험 분석 응답 약 5~6초
수정안: 응답 이후 별도 완료
```

## 검증 결과

- `.\gradlew.bat clean test` 전체 176개 통과
- 개인정보가 실제 LLM 호출 전에 제거되는 통합 테스트 통과
- 수정안 비동기 상태 전이와 실패 분리 테스트 통과
- 이번 마스킹 변경에서 새로 추가된 테스트는 단위 3개, 통합 1개다.
- 후속 개발 중에는 관련 `--tests`만 실행하고 공통 경계 변경 완료 시 전체 테스트를 한 번 실행한다.

## DB 적용 정책

현재는 영구 DB 없이 H2 `ddl-auto=create-drop`을 사용하므로 증분 마이그레이션 파일을 두지 않는다.
영구 DB를 도입할 때 현재 엔티티 전체를 기준으로 초기 스키마를 만들고, 그 이후부터 증분
마이그레이션과 백필·롤백 정책을 함께 관리한다.

또한 `docs/risk-analysis-guardrail-handoff.md`는 이전 변경의 전달 문서이며, 수정안 실패 시
Rule-only로 전환한다는 과거 정책이 남아 있다. 현재 정책은 HYBRID 유지와
`revisionStatus=UNAVAILABLE`이므로 이번 작업 판단에는 이 문서를 우선한다.

## 배포 확인과 롤백

- 확인 지표: `/analyze`와 전체 응답 p95, Rule-only 전환율, 수정안 `UNAVAILABLE` 비율,
  마스킹 실패율, timeout·5xx
- 롤백 조건: 오류율 또는 마스킹 오탐 급증, 지속적인 AI timeout, 수정안 상태 전이 실패
- 롤백 방법: 이전 백엔드 버전으로 복구하고 AI 장애 중에는 기존 Rule-only 정책을 유지한다.
