# TeacherHub AI 품질 운영 플레이북

## 목적

AI 기능을 "한 번 동작하는 기능"이 아니라 측정하고 개선할 수 있는 제품으로 운영하기 위한 기준이다.
핵심 순서는 **가드레일 → 골든셋 → 평가 → 배포 게이트 → 운영 모니터링 → 개선 제안**이다.

Self-evolving은 에이전트가 운영 중에 자기 프롬프트를 즉시 바꾸는 기능을 뜻하지 않는다.
운영 실패 사례를 수집하고, 개선안을 만들고, 오프라인 평가와 사람 승인을 거쳐 다음 버전을
배포하는 통제된 반복 학습 루프를 뜻한다.

## 1. 현재 상태와 가장 큰 간극

현재 코드에는 다음 기반이 있다.

- 개인정보 마스킹 경계와 마스킹 테스트
- CSV v1.1 72행을 사용하는 실제 Rule 탐지기와 LLM 탐지기 인터페이스
- 두 결과의 병합, 점수 계산, 근거 저장
- 위험도별 교사/관리자 검토와 Emergency 안전 잠금
- 모델명과 temperature 저장
- 단위·Controller·통합 테스트 및 GitHub Actions CI

Rule 탐지기는 실제 사전을 사용하지만 LLM 문맥 판단, 수정안 생성기와 교사 지원 생성기의
품질은 외부 모델과 평가 데이터에 의존한다. 현재 테스트는 Rule 매칭과 파이프라인의 연결 및
업무 규칙을 검증하지만 실제 AI 품질을 보장하지 않는다. 외부 모델 연결보다 먼저 평가 데이터와
배포 기준을 만들어야 한다.

## 2. P0: 안전 계약을 먼저 고정한다

각 기능마다 아래 표를 작성하고 코드·테스트·운영 정책을 일치시킨다.

| 기능 | 결정론적 가드레일 | LLM 역할 | 실패 시 동작 | 사람 승인 |
|---|---|---|---|---|
| 민원 위험 분석 | PII 마스킹, 명확한 금칙 패턴, 점수·상태 규칙 | 문맥형 위험 태그와 근거 제안 | 제품 정책으로 명시 | High/Emergency 재검토 |
| 교사 답변 초안 | 권한, 상태, 안전 잠금, 길이·형식 검증 | 답변 초안 생성 | 초안 미제공 | 교사가 수정 후 전송 |
| 완충 요약 | 권한, 입력 제한, 출력 검증 | 안전한 요약 생성 | 원문 노출 여부를 정책으로 명시 | 필요 시 교사 확인 |
| 프롬프트 개선 | 평가 게이트, 버전 관리, 롤백 | 후보 프롬프트 제안 | 기존 버전 유지 | 승인 후 배포 |

가장 먼저 확정할 질문은 "LLM 또는 마스킹 실패 시 원문 제출/노출을 허용할 것인가"다.
기능별 `fail-open`/`fail-closed` 정책, 사용자 안내, 재시도, 관리자 알림을 테스트 가능한 문장으로 정한다.

## 3. 골든셋 v1

처음부터 200개를 억지로 만들기보다 검수된 50개로 시작해 실제 실패 사례를 반영하며 200개 이상으로
확장한다. 개인정보가 제거된 합성 데이터 또는 사용 동의를 받고 비식별화한 데이터만 사용한다.

### 권장 구성

- 일반 문의와 감사 표현 20%
- 욕설·모욕 15%
- 직접·간접 위협 15%
- 법적 조치 언급 10%
- 개인정보 노출 10%
- 반복 민원 10%
- 부당 요구 10%
- 여러 태그가 섞인 사례 5%
- 오탈자, 은어, 우회 표현, prompt injection 등 적대 사례 5%

각 위험 범주에는 명백한 양성, 명백한 음성, 경계 사례를 함께 둔다. 학교 현장의 한국어 존댓말,
반어법, 인용문, 교사를 향한 표현과 제3자를 설명하는 표현을 포함한다.

### 케이스 스키마 예시

```json
{
  "caseId": "THREAT-001",
  "datasetVersion": "v1.0",
  "input": "비식별화된 민원 문장",
  "context": {"previousMessages": [], "repeatCount": 0},
  "expected": {
    "tags": ["THREAT"],
    "riskLevel": "HIGH",
    "mustBlock": false,
    "piiLeak": false
  },
  "rubric": {
    "requiredEvidence": ["위협으로 판단한 구절"],
    "notes": "간접적 불이익 암시"
  },
  "review": {"reviewers": 2, "status": "AGREED"}
}
```

정답은 한 사람의 직감이 아니라 최소 두 명의 독립 라벨과 불일치 조정으로 확정한다. 경계 사례는
억지로 단일 정답을 만들지 말고 허용 가능한 태그·등급 범위와 사람 검토 필요 여부를 기록한다.

## 4. 평가 지표

### 배포 차단 지표

- 개인정보 원문 외부 전송 또는 출력 누출: 0건
- 인증·권한·Emergency 차단 규칙 회귀: 0건
- 결정론적 골든 케이스 불일치: 0건
- 파싱 불가 또는 허용되지 않은 enum 출력: 0건
- 기존 기준선보다 안전 중요 범주의 recall 하락: 허용하지 않음

### 품질 지표

- 태그별 precision, recall, F1 및 macro F1
- 특히 `THREAT`, `PRIVACY`, `PROFANITY`의 recall
- 위험 등급 정확도와 한 단계 이상 과소평가한 비율
- 근거 구절의 유효성
- 답변 초안의 공감성, 사실 충실성, 과도한 약속 금지, 행동 가능성
- 사람 평가와 LLM judge 평가의 일치율
- 교사의 초안 채택률, 수정 거리, 재생성률, 관리자 override 비율

안전 기능에서는 평균 점수 하나로 통과시키지 않는다. 심각한 false negative 한 건이 평균 향상보다
중요할 수 있으므로 범주별 하한과 금지 실패를 별도로 둔다.

## 5. 평가 방법

1. **코드 검사**: 권한, 상태, 스키마, 개인정보, 제한값을 단위·통합 테스트로 검사한다.
2. **정답 비교**: 태그·등급·차단 여부를 골든셋과 비교한다.
3. **규칙 기반 출력 검사**: PII 재노출, 금지 문구, 길이, JSON schema를 검사한다.
4. **LLM-as-a-judge**: 문맥 적합성처럼 규칙화하기 어려운 항목을 명시적 rubric으로 채점한다.
5. **휴먼 라벨링**: 표본과 모든 치명 실패를 사람이 검토한다.

LLM judge는 정답 그 자체가 아니다. judge 모델과 프롬프트를 버전으로 고정하고, 평가 순서를 섞으며,
후보 이름을 가리고, 같은 표본에 대한 사람 점수와 정기적으로 비교한다. G-Eval류 방식은 평가 기준과
채점 절차를 구조화하는 데 활용하되 최종 배포 책임을 넘기지 않는다.

## 6. 배포 게이트

프롬프트, 모델, temperature, 전처리, 병합 정책, 위험 점수 중 하나라도 바뀌면 새 AI 버전으로 본다.

1. 변경 전 기준선 결과를 저장한다.
2. 단위·통합 테스트와 전체 골든셋을 새 버전에 실행한다.
3. 확률적 변동을 보기 위해 중요한 케이스를 여러 번 실행한다.
4. 이전 버전과 지표·실패 케이스를 나란히 비교한다.
5. 치명 실패가 없고 범주별 하한을 만족할 때만 사람 승인을 받는다.
6. 소량 트래픽 또는 shadow 평가로 시작한다.
7. 롤백 조건을 넘으면 즉시 이전 버전으로 되돌린다.

평가 결과에는 최소한 코드 commit, dataset 버전, prompt 버전, model 식별자, 생성 설정,
실행 시각을 기록한다. 같은 입력·설정으로 재현할 수 있어야 한다.

## 7. 운영 드리프트 감시

에이전트가 이유 없이 스스로 나빠진다기보다 입력 분포, 사용자 표현, 정책, 모델 제공자의 버전,
프롬프트와 주변 코드가 변해 초기 평가셋의 대표성이 떨어지는 것이 주된 원인이다.

주간 또는 배포 단위로 다음을 비교한다.

- 태그·위험 등급 분포와 `UNKNOWN`/`BOUNDARY` 비율
- 교사 및 관리자 override 비율
- 안전 차단률, AI 실패율, fallback 비율
- 초안 채택률, 수정 거리, 재생성률
- 지연 시간 p50/p95, 토큰 사용량과 케이스당 비용
- 새 표현·새 민원 유형의 비율
- 모델·프롬프트·데이터셋 버전별 성능

임계값을 넘은 사례는 자동 재학습하지 않고 검토 큐로 보낸다. 재현 가능한 비식별 사례로 만든 뒤
라벨링하고 골든셋에 추가한다.

## 8. 통제된 Self-evolving loop

```text
운영 로그/사용자 수정/override
→ 개인정보 제거 및 실패 사례 후보화
→ 사람 라벨링과 원인 분류
→ 프롬프트·룰·코드 개선안 생성
→ 고정 골든셋 + 신규 회귀셋 평가
→ 사람 승인
→ canary/shadow 배포
→ 모니터링 및 필요 시 롤백
```

메타 프롬프팅이나 GEPA 같은 최적화 기법은 "후보 생성기"로만 사용한다. 평가셋 과적합을 막기 위해
학습/개발셋과 최종 holdout셋을 분리하며, 최적화 도구가 holdout 정답을 보지 못하게 한다.

## 9. TeacherHub 실행 순서

### 1주차: 측정 가능한 기반

- [ ] 안전 계약 표의 실패 정책을 팀에서 확정한다.
- [ ] 비식별 골든셋 50개와 라벨링 가이드를 만든다.
- [ ] CSV Rule 후보와 고정 LLM fake를 기준으로 평가 runner의 입출력 schema를 먼저 고정한다.
- [ ] 태그별 confusion matrix와 위험 등급 결과를 출력한다.
- [ ] prompt/model/dataset 버전을 저장할 위치를 정한다.

### 2주차: 실제 모델 연결 전 게이트

- [ ] 외부 LLM adapter에 timeout, retry, schema validation, circuit breaker를 둔다.
- [ ] PII·권한·Emergency 치명 테스트를 CI 필수 게이트로 만든다.
- [ ] LLM judge rubric과 휴먼 평가 양식을 만든다.
- [ ] 이전 버전 대비 평가 리포트를 PR에 첨부한다.
- [ ] rollback 가능한 prompt/model 버전 선택 방식을 만든다.

### 이후: 운영 개선

- [ ] 실제 실패·수정 사례를 주기적으로 라벨링한다.
- [ ] 200개 이상의 대표 골든셋과 별도 holdout셋으로 확장한다.
- [ ] drift 대시보드와 임계값 알림을 구성한다.
- [ ] 개선 후보 생성은 자동화하되 배포 승인은 자동화하지 않는다.
